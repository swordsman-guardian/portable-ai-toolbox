# 基础能力实施方案

本轮范围由用户确认：多开、归档可靠性、内置 Python/uv 环境管理。CC Switch、加密保险箱、更多 harness 和图形界面留到下一阶段。

## 设计约定

### 多会话

- 每个窗口有独立 GUID、工作目录、配置副本和进程树。
- 临时目录需要所有权标记、进程身份和锁；不能仅凭目录名删除。
- 未知旧目录、无法确定是否活跃的目录保留；不能影响宿主已有 AI 会话。
- 供应商和模型在启动时形成该进程的环境快照。
- 新归档布局为 `sessions/<host>/<harness>/runs/<session-id>/`，各窗口独立写入。
- 启动时只读恢复新布局和旧布局；冲突的原始归档必须保留，不拼接分叉的对话。

### 归档

- JSONL 只复制已经完整写入的行，并限制复制字节范围。
- 记录偏移与实际文件不一致时可修复，避免重复追加。
- JSON 和清单替换保留恢复副本；不承诺 FAT32 硬件断电绝对原子。
- 归档路径必须限制在目标目录之内。
- 保存成功状态依据实际结果，30 秒是调度间隔而非最大丢失保证。

### Python/uv

- 默认沿用现有内置 uv 和 Python，不批量下载新版本或依赖。
- 工具箱不自动使用宿主 Python，不修改宿主全局环境。
- 项目要求与内置版本兼容时显式选择该解释器；不兼容则明确报告缺失条件。
- 项目环境建立在本次工作目录内，不替换用户项目的 `.venv`。
- 每个窗口绑定一个项目，普通 Python 和 uv 项目/包命令显式指向该会话环境；切换项目需新开窗口。
- 解释器就绪、虚拟环境创建完成、项目依赖安装完成是不同状态。
- U 盘保留解释器和包缓存，虚拟环境可重建；不承诺虚拟环境换盘符直接可用。
- 下一阶段再扩展经过校验的解释器下载安装、依赖同步和离线准备。

## 验收

1. 活跃的 A 会话不被 B 的启动或退出清理。
2. 已终止且属于本工具的残留可清理；未知目录不删除。
3. 两个会话独立保存，重启可以恢复各自的项目历史。
4. 大于 4 KB 的 JSONL 多轮追加包含半行时不会重复或损坏；长行同样正确。
5. 清单或写入中断时能够恢复上一份有效记录，恶意路径不能写出目标目录。
6. Python/uv 的宿主环境污染被阻断，项目版本不匹配有明确状态。
7. 不同项目环境隔离，同一环境标识可复用，未装依赖不显示为全部就绪。
8. 在 Windows PowerShell 5.1 下运行有效测试，新增脚本带 UTF-8 BOM。
9. GPT-6 Sol 审查后修复阻塞问题，再做最终回归。

本轮测试使用合成数据和测试专属进程；不发起付费模型请求，不读取或显示实际 API 密钥，不对 U 盘执行格式化或真实拔盘。

## 下一阶段顺序（本轮不实施）

1. **先定义加密与解锁生命周期。** 区分盘内静态密钥、会话期间需要使用的凭据、本机临时副本和待恢复副本；设计主密码、锁定、备份与恢复流程。确定这些边界后再实现保险箱，避免新接入工具继续各自保存明文密钥。加密不能解决使用中的电脑本身不可信的问题。
2. **再接入 CC Switch。** 先核查它的配置格式、运行方式和授权条件，明确供应商、模型与密钥的唯一管理来源。供应商切换先影响新窗口；是否更新正在运行的窗口需要单独设计和验证。
3. **按统一接口逐个扩展 harness。** 每个适配器明确启动参数、运行时需求、配置位置、密钥注入、历史归档与退出行为。优先接入实际常用的两三个，通过多开、恢复、拔盘和离线条件验收后再扩大覆盖面。
4. **整理交互。** 首页展示当前项目、工具、供应商、Python 环境状态和最近一次保存结果；把缺少解释器、缺少依赖、归档失败分别提供明确处理入口。待恢复会话应能被发现并引导恢复。

环境数量采用“少量共享解释器 + 各项目独立环境”：默认保留现有一份 Python，真实项目需要不同次版本时再补装；不要为每个 harness 捆绑完整 Python，也不要为“可能用到”预装大量依赖。本轮的项目环境随窗口建立，后续再考虑可重建缓存与离线依赖准备。
