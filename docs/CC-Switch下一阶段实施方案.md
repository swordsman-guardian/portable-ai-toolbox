# 下一阶段：CC Switch 加密、联网与代理方案

日期：2026-09-29。状态：加密会话已实现并通过合成与原生窗口验收；真实用户配置尚未迁移。原生联网检测已通过，菜单 8 提供显式联网入口；原生代理尚未接通。下文保留阶段设计背景；实际交付范围以 [加密接入验收](CC-Switch加密接入验收.md) 和 [联网代理验证](CC-Switch联网代理验证.md) 为准。

## 不变的约束

官方 CC Switch 原包不改源码、不打补丁；隔离和运行组件随 U 盘携带；普通 Windows 用户免安装；宿主已有 CC Switch 可并行；不更改宿主 harness 配置、系统代理、持久防火墙规则或 loopback 豁免。不同电脑不绑定本机账户。当前验证范围仍为 Windows x64，企业策略可能阻止运行。

## 实施顺序

第一批：加密配置生命周期；并行做最小出站网络与原生代理连通探针。第二批：开放验证通过的联网检测。第三批：依据探针结果接入代理，不预先承诺原生代理能在全部约束下开放。

## 1. 配置加密与解锁生命周期

当前 cc-switch-store 保存明文 generation，同时 Export-CcStoreProfile 导出含凭据的 Claude settings.json。仅加密数据库或增加一个加密备份均不够。已有 vault.ps1 提供认证加密，但 portable-profile.ps1 是限 16 MiB 的停止后手动存档，不能直接当成实时自动存储。

目标流程：输入主密码一次 → 解锁盘内配置 → 恢复到受管本地会话 → 官方程序使用 → SQLite backup及普通文件稳定检查 → 加密新代 → 验证可解密与完整性 → 提交U盘指针。当前代和上一成功代均为密文。锁定时关闭持钥进程和会话，清理本地副本。

工程任务：
- 在store层增加版本化加密格式，完整覆盖配置文件、数据库及含敏感内容的清单。复用既有认证加密实现前复核容量、内存占用和性能；不把磁盘配额简单调大后宣称可用。
- 会话随机数据密钥由主密码派生的密钥加密保护；成熟密码库负责随机数、加密认证和密钥派生。避免每15秒重复昂贵的主密码派生。每个快照使用新随机值，密钥只留在会话内存，不写命令行、日志或U盘明文文件。
- 替换当前明文Claude投影。可信本地会话管理器在解锁后读取当前供应商，通过限本用户、受验证的本机通信交给启动器；已开启工具窗口维持启动时配置，新窗口取最新成功保存版本。通信仅暴露固定供应商操作，不接受任意文件路径或命令。
- 解锁状态、供应商来源、保存状态在工具箱中统一显示。同一解锁会话可服务多个工具窗口；换电脑输入同一个主密码即可恢复，不需重新配置供应商。无需重配不等于无需解锁。
- 先生成并验证完整密文，再切换版本指针，最后清理精确列出的旧明文generation、投影、备份与暂存文件。迁移失败继续保留可恢复的原配置，不能静默回退到明文运行；报出仍有明文的事实。
- 复核运行时、日志、归档是否携带凭据。加密保护的是U盘静态数据，不承诺对恶意宿主、进程内存、分页文件或已删除历史块提供保护。
- 拔盘看护与同步保存拆开，可信看护代码先驻留本地，防止磁盘I/O阻塞检测。停止受管进程后清理明文；需要保留恢复内容时优先留下加密恢复包，不沿用当前失败时保留明文目录的策略。

验收：错密码/密文篡改不启动；正常切换、关闭、重开和换电脑恢复；使用高辨识度合成密钥检查U盘所有受管输出中没有其明文；失败提交仍可恢复上一密文代；活跃多窗口互不覆盖；拔盘、崩溃及保存失败分别验证。

## 2. 联网检测

现有AppContainer的capability数量为0，不能访问网络。第一步用合成探针验证internetClient出站能力，保留现有文件与命名空间隔离。网络能力不等于供应商域名白名单；不要把直接放行出站网络描述成逐域名强制限制。

分别验证DNS、TLS、HTTPS、重定向和超时；保留证书验证。先用无密钥测试端点，付费模型请求只在用户明确触发测试时发送。区分“网络可达”“鉴权成功”“模型请求成功”，状态码401也说明连接成功但鉴权失败，不混为一谈。

出站网络探针成功后，再实测官方GUI检测入口。不自动继承宿主代理变量，不更改全局代理或系统信任证书。内网地址、VPN、DNS和127.0.0.1代理单独判定支持范围，不能以关闭隔离作为兼容兜底。开放联网后重跑宿主写入拒绝及双实例隔离测试。

代码落点：appcontainer-probe.ps1 的profile capability与进程SECURITY_CAPABILITIES必须一致；cc-switch-isolated.ps1负责能力选择和状态输出；测试应验证实际进程token及真实请求，而非只检查环境变量。

## 3. 代理：先证明免安装可行

这里区分三种场景：原生CC Switch接管harness的本地路由；应用向上游HTTP/SOCKS代理发请求；修改Windows系统代理。目标先做前两种，系统代理不纳入本项目。

官方v3.20.4代理会监听本地TCP端口并写入harness路由配置。当前harness在普通工具箱进程中，CC Switch在AppContainer内，两者间loopback通信不能假定可用。微软文档列出的部分loopback豁免方案需要管理员权限，与免安装普通用户目标冲突。

先验证四件事：
1. 普通权限下，隔离内原生代理能否监听，外部受管harness能否连接。
2. 本机CC Switch已占用其默认端口时，U盘会话能否独立选端口并正确回写。
3. 代理退出/崩溃/拔盘后，harness不会误连本机另一个进程或重用端口；新会话不会读到上次机器的127.0.0.1地址。
4. 流式响应、取消、工具调用及错误传递正确；不记录Key或默认存储请求正文。

只有零提权、零系统规则修改的实测通过，才开放“原生代理”。若需系统豁免，维持原生代理关闭。替代方案是U盘自带独立代理，由可信工具箱管理进程运行，只绑定loopback并使用会话鉴权、独立端口，按受管配置转发；此项必须明确叫“工具箱代理”，不能冒充原生CC Switch接管，也不保证与官方全部路由特性等价。先适配Claude基础转发，再逐项增加其他harness。

## 首批交付标准

插盘解锁一次，配置自动恢复；供应商由用户选择的来源提供；原生联网检测可给出可解释的结果；U盘不留下受管凭据明文；本机CC Switch并行且宿主配置不变。代理探针必须给出可复現的结果和选择依据，不能为开放按钮放弃隔离约束。
