# CC Switch 作为唯一配置入口

用户方向确认：2026-09-29。该文件记录接下来的产品要求，不表示相关改造已全部完成。

## 使用方式

CC Switch 是受支持 harness 的供应商、API Key、模型、MCP、Skills 等配置的唯一编辑入口。优先使用其原生自身更新和工具安装/更新界面。工具箱只保留启动、解锁/锁定、项目选择、运行状态、恢复和退出等便携生命周期操作。

原工具箱供应商编辑、凭据编辑、配置导入和“工具箱 / CC Switch 两套供应商来源切换”应在迁移验收后退出日常菜单。后台仍需加密读写、运行期配置生成、备份和回滚；这些属于保存/恢复机制，不成为第二个用户配置入口。CC Switch 未覆盖的工具功能先明确支持范围，不暗中退回另一套配置。

## 升级适配目标

- CC Switch 自身：用户从官方界面发起；验证官方更新实际下载/执行的产物和路径、是否启动安装器或退出当前进程树。更新必须最终保存为 U 盘上的下一版本，失败时保留可恢复的程序和对应配置。
- harness：用户从 CC Switch 管理；工具发现、Node/npm及安装目标必须限定为本盘受管副本，禁止选择或更新宿主安装。显式固定 PATH 并不足以证明这一点，仍须审计原生工具发现和更新路径。
- 所有安装/更新的子进程仍须留在隔离边界内，退出重启继续继承隔离。不能为更新放开宿主写入，也不能将本机安装器当作便携升级成功。
- 官方 CC Switch 保持原包。若某个原生升级流程没有免修改的可靠便携接入方式，记录具体阻塞；不能先承诺只靠环境变量即可完全接通，也不自动引入长期源码分支。

## 当前差距

当前运行的是受校验的临时 CC Switch 副本，USB 程序包版本校验固定为 3.20.4；运行期配置快照不会自动把更新后的可执行文件变成 USB 新版本。隔离环境也没有向原生 CC Switch 提供完整的盘内 Node/npm 与 harness 安装管理链路。因此上游有升级能力，不等于当前项目已经接通这些能力。

## 实施顺序与验收

1. 用合成配置审计和验证原生自身更新、工具发现及安装目标，不触碰宿主程序或真实配置。
2. 接通受管运行环境与更新结果的 USB 持久保存，验证重插后版本保留、失败回滚及配置兼容性。
3. 将现有真实配置一次性迁移进 CC Switch；逐项核对供应商、密钥和模型可用后，再退役旧入口。不能先删除现有 keys.env、供应商定义或保险箱。
4. 日常启动统一读取已解锁 CC Switch 状态；锁定或读取失败明确停止，不自动采用第二套供应商来源。清理保留旧数据需列出精确对象，不能随迁移静默批量删除。
